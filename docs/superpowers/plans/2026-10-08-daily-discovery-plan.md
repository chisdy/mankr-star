## 1. 已确认范围

在现有应用增加「每日热点」入口 `/discover`，按四个固定垂直频道展示每日内容。用户切换频道、查看原文、收藏内容；获取规则由项目维护。

| 频道 ID    | 名称            | 获取与归类方向                        |
| ---------- | --------------- | ------------------------------------- |
| `ai`       | AI / 大模型     | LLM、模型、Agent、RAG、推理与 AI 应用 |
| `frontend` | 前端开发        | React、Vue、浏览器、CSS、Web UI       |
| `backend`  | 后端 / 基础设施 | 数据库、服务框架、云原生、可观测性    |
| `tools`    | 开发工具        | CLI、编辑器、IDE、自动化、开发效率    |

第一版：

- 接入 GitHub、Hacker News、经过验证的公开 RSS/Atom。
- 每个频道最多展示 20 条，默认进入 AI 频道；来源不足时允许少于 20 条。
- 每天北京时间 08:00 后启动一次同步，分片完成后发布；显示实际更新时间，不承诺 08:00 已生成完整榜单。
- 摘要使用来源简介或清理后的摘录，分类使用固定规则，不调用付费 AI。
- 收藏复用已有收藏接口；收藏后的 AI、文件夹、标签处理遵循原有流程。
- 沿用项目已有公开浏览开关：开启时访客可浏览热点，收藏需要登录。

第一版不包含：搜索框、用户关键词订阅、自定义分类、自定义 RSS、历史榜单界面、通知、X 接入、自动将全部热点加入收藏库。X 与热点 AI 摘要作为后续可选扩展，不增加占位设置或无效控件。

## 3. 数据来源与规则

### 3.1 GitHub：候选仓库中的增长发现

- 使用官方仓库搜索 API。仅搜索公开、未归档、非 fork 的仓库；固定 Topics、活跃时间窗和最低 Stars 条件在配置文件维护。
- 初始 Topics：AI 使用 `llm` / `ai-agents`，前端使用 `react` / `vue`，后端使用 `database` / `cloud-native`，工具使用 `developer-tools` / `cli`。每个 Topic 分别请求 Stars 与最近更新排序，单页最多 25 个结果；每日最多 16 次搜索，不无限翻页。
- 搜索结果合并去重，再按频道保留候选；相同仓库使用 GitHub 数字仓库 ID 识别，URL 改名不切断快照身份。
- 每频道跟踪池最多 20 个仓库，全局去重后最多 80 个；保留近期候选的基线，当前搜索已返回其数据时不再单独获取。池中落选候选保留 7 天观察，新增与保留候选各分配 10 个名额，一侧不足时允许另一侧补位，不能每次只保留累计 Stars 最大的老仓库。
- **补充于评审 R3：** 跟踪池按 `(channel_id, github_repo_id)` 独立维护，GitHub 频道任务的 `pool_state_json` 固化本日选中成员的 `joined_day`、`last_search_hit_day` 和新/保留类型；新日读取最近成功的同频道池状态构建下一池。搜索再次命中才更新 `last_search_hit_day`，补充详情请求、HN/RSS 提及及其他频道命中均不延长该频道的保留期。超过 7 个北京时间自然日未命中的成员退出；7 天是最长观察期，仍受 20 个名额约束。新候选按固定查询顺序、结果位置、数值仓库 ID 取前 10 个；保留成员按最后搜索命中日降序、数值 ID 升序取前 10 个，两侧不足依同一顺序补位。当天池名单写入后续跑不重新挑选，只有任务成功后才成为下一日输入；全局补抓按仓库 ID 去重。
- Token 已配置时，对跟踪池中搜索未返回的仓库补充元数据请求，最多 80 次/日；没有 Token 时省略补充请求，尊重实际剩余额度，接受基线覆盖率较低。
- 这是本项目维护的候选池榜单，不宣称等同 GitHub 官方 Trending 或覆盖全站。

**增长口径：**

1. 只对来源任务成功的快照做比较；基线取前一北京时间日期的有效快照。
2. 实际采样间隔须在 20–36 小时内；记录并返回两个采样时间，文案使用「较昨日采样 +N」。间隔不合格时返回增量缺失，而不是补成 0。
3. 首次发现仅建立基线，累计 Stars 可以展示，增长字段为 `null`；初次榜单标为「新发现 / 推荐」，不假装有今日增长。
4. 净增量允许负数。增长排序采用非负增长信号，但原始负值必须保留；真实 0、缺失基线、负增量是不同状态。
5. 有有效增量的仓库按增长优先；新发现候选有独立展示名额，不与累计 Stars 直接混算增长分。

### 3.2 Hacker News：原生热门与讨论

- 使用官方 `topstories` / `beststories` 列表，合并后按来源顺序限制为 40 个候选，并按游标逐条获取详情。全部频道共享这一批抓取结果。
- 保留标题、原文 URL、HN 讨论 URL、分数、评论数和发布时间。无外链的 Ask/Show 条目使用 HN 讨论页作为内容 URL。
- 只保留最近 7 天的有效条目；删除、dead、非 story 项跳过。
- 在标题、可用简介和域名上做固定归类，使用完整词、短语和明确别名；`go` 等短词不能简单子串匹配。证据不足的条目不入频道，单条最多进入两个频道。
- 使用 HN 原生顺序与分数排序，卡片标明「HN 分数 / 评论」，不等同于 GitHub Stars。

### 3.3 RSS/Atom：垂直更新

首批来源如下，2026-10-08 已检查均返回 200 且可解析为 RSS；实施时仍须验证日期、链接和解析 CPU。失败的来源不写入启用清单。

| 来源 ID       | Feed                                   | 主要频道        |
| ------------- | -------------------------------------- | --------------- |
| `huggingface` | `https://huggingface.co/blog/feed.xml` | AI              |
| `webdev`      | `https://web.dev/static/blog/feed.xml` | 前端            |
| `cloudflare`  | `https://blog.cloudflare.com/rss/`     | 后端 / 基础设施 |

实测：Hugging Face Feed 约 258 KB、874 条，web.dev 约 5 KB、10 条，Cloudflare 约 286 KB、20 条。GitHub Blog Feed 超过 1 MiB 初始响应预算，本期不启用；开发工具频道先使用 GitHub 与 HN，RSS 不要求覆盖全部频道。

- 最多启用 4 个 Feed，每个最多读取 30 个条目，只保留 7 天内有可信日期的内容；缺失日期或明显未来日期不当作今日更新。
- Feed 分配频道是候选范围，再结合技术关键词排除招聘、营销、活动等无关条目。
- 支持 RSS 2.0 与 Atom，选择兼容 Workers 的有维护流式 XML 解析器；收集到 30 个条目即停止正文读取，避免为展示少量内容解析 Hugging Face 的全部历史条目。不通过简单正则解析整个 XML，不启用 DTD 或外部实体。
- 获取固定白名单 Feed；单响应初始上限 1 MiB，超时 8 秒，重定向最多两跳且逐跳检查目标。实现时复用 `url-ssrf.ts` 的现有校验能力，原文外链不在同步时继续抓取。
- HTML 仅清理为纯文本摘录；页面使用 React 文本渲染，不直接执行或渲染原始 Feed HTML。
- 缓存 ETag / Last-Modified，处理 304 时明确沿用上次成功内容与原始时间。
- **补充于第三轮评审 R13（来源字段边界）：** 发现层原始内容 URL 与规范化 URL 均最多 2,048 字符，超限拒绝，不截断身份；共享发现响应的 item/evidence URL 使用同一上限，原收藏和导入契约不改。标题最多 500、纯文本摘要最多 2,000 个 UTF-16 code units，并在截取前后保证 Unicode 完整，不能产生或保存孤立 surrogate。RSS GUID/Atom ID 在 32,000 字符内按完整值识别；超过 500 字符使用完整值的 SHA-256 并保留 Feed 命名空间，超过读取上限明确报错。原始 ID 与摘要编码必须使用互不相交的表示，避免短 GUID `sha256:<某长 GUID 的 hash>` 与该长 GUID 生成同一 external ID；定义兼容旧游标的读法，不改已成功快照。条件头按 ETag 1,024、Last-Modified 128 字符验证，拒绝控制字符。GitHub `full_name` 与规范化仓库 URL 的身份必须一致；不通过截断名称接受不合法身份。上述边界在来源解析、持久化和响应之间统一验证。
- RSS 展示名称为「最新更新」，按发布时间排序；没有真实互动数据时不制造热度分数。
- **补充于评审 R7：** 「读取前 30 条即停止」只适用于已验证最新条目在前的白名单 Feed。P0/P2 用完整来源样本核对可信日期顺序，并保存相应 fixture；无法确认最新优先的 Feed 本期不启用，不能在截断后排序来声称覆盖最新内容。回归样本包含「前 30 条全是旧内容、第 31 条才是新内容」，该来源应被拒绝启用。固定来源在运行时出现顺序违例时记录来源错误并保留上次成功内容。

## 4. 合并、排序与展示

### 4.1 去重

内容层统一规范化 URL，复用已有 `canonicalizeUrl` / GitHub URL 规则，只移除已知跟踪参数，保留会影响内容身份的参数。HN 和 RSS 指向同一文章、HN 指向已有 GitHub 仓库时，合为一条内容，保留多个来源及各自指标。

GitHub 内容在 `discovery_items.github_repo_id` 上增加 nullable UNIQUE 约束，按数字 ID 优先查找；更名时复用原 `item_id`，更新当前 URL、保留旧 URL 别名。新 URL 已有通用内容记录时，在事务内将旧记录标记 `merged_into_id`，释放其唯一当前 URL，再更新胜出记录；旧版本继续引用原记录和固化展示字段，后续新版本解析归并后的身份并去重，不改写已发布榜单。两个已知不同 GitHub 数字 ID 不自动归并，按路径复用冲突处理。来源导入先解析稳定身份/现有别名，再按规范化 URL upsert，唯一约束冲突必须重读并合并，不产生第二份增长基线。

**补充于评审（实现边界）：** 发现层通过新 `normalize.ts` 包装现有 URL 规范化，不修改共享 `canonicalizeUrl` 或 `detectSourceType` 的既有参数、返回形状和处理规则；原收藏、浏览器导入及扩展继续使用旧契约。需要多语句原子归并时使用 D1 原生 `DB.batch`；不要把「事务内」解释为未验证的交互式事务回调。[D1 batch 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

每个频道同一内容只出现一次；允许内容出现在两个相关频道。去重后不将 HN 分数与 Stars 相加。没有外链的 HN 讨论保持为独立内容。

### 4.2 组合列表

- 每个来源先内部排序，再按 GitHub : HN : RSS = 6 : 3 : 1 的目标比例交错展示。
- 跨源重复项占一个位置，保留多来源证据；来源不足时其他有效来源可补位，总数不超过 20。
- 组合列表是编辑规则形成的推荐顺序，UI 不展示虚构的跨平台统一热度分。
- 列表标题、摘要和 URL 在发布版本中固化，避免同步中的内容更新让已发布榜单发生半更新。

### 4.3 页面

- 沿用原应用壳、字体、颜色和组件；四频道使用可访问的标签页，移动端可横向滚动。
- 频道通过 `?channel=ai|frontend|backend|tools` 保留状态；未知值回退 AI。
- 页面只提供频道切换与列表，不增加搜索、关键词输入、分类编辑或订阅管理。
- 卡片显示标题、短摘要、来源、对应来源指标、内容时间、原文入口和收藏入口。
- 展示最后发布时间及来源状态。当天更新尚未完成时保留上一版；部分来源沿用旧内容时逐来源显示最后成功日期，超过 7 天的旧来源结果不再混入新榜单。
- 区分首次初始化、频道确实无结果、同步进行中、部分失败、有旧结果的失败、完全没有可用结果。
- 页面刷新只重新读取已发布数据，不触发外部抓取。
- **补充于设置页增补（§21）：** 登录用户在「设置 → 每日热点」保存实例开关。开启但无首版时设置页显示等待首次同步，导航仍要求 `enabled && ready`；保存开关和刷新均不触发抓取。关闭隐藏入口及热点读接口内容，停止后续同步，保留已发布榜单与原收藏。

| `discovery_editions`      | `id`、`edition_day`、`channel_id`、修订号、`draft/published`、来源任务引用和状态、规则版本、发布时间；唯一 `(edition_day, channel_id, revision)`                                                                                                                        | 频道的不可变发布版本及来源新旧状态                                                                                    |

索引覆盖任务的状态/重试时间、来源身份/观测日期、最新已发布频道版本及版本内排名。JSON 字段有长度和 schema 校验；不保存完整页面、完整 README 或整份 Feed。

**补充于第三轮评审 R13（存储容量）：** 明列既有 migration 的 JSON CHECK：配置/池状态各 65,536、游标 262,144、单 observation 16,384、单冻结条目 32,768 字符；同时遵守平台每个绑定值/行的字节限制。配置校验使用不超过 64 KiB 的 UTF-8 序列化大小。紧凑游标可以去掉可确定重建的重复字段，但必须保留挑池前每频道全部 100 个搜索输入及所需详情，恢复后来源文本和内容身份一致，不能靠减少池规模或缩短已接受摘要通过 CHECK。以引号、反斜线、原有 PUA 字符、有效补充平面字符、截取边界及非法孤立 surrogate 验证编码/恢复；不能只用等长 ASCII 填充证明最坏容量。已应用迁移保持原样。

**补充于评审 R2：** 同日各来源任务共享创建时固化的有效规则快照，包含查询、Feed 白名单、分类词表、排序及预算参数；任务恢复使用自己的快照，不能使用新部署的当前配置继续旧游标。`execution_schema_version` 标识执行器可兼容的数据/算法版本；遇到不支持的旧版本时终止该任务并记录 `RULE_VERSION_UNSUPPORTED`、继续展示旧榜单，下一日创建新版本任务，不混合规则也不重建同日成功任务。来源成功后，其 observations、规则快照和池状态不可改写；失败任务只能在规定重试范围内续跑，不得覆盖成功基线。

**补充于复审 R9（P1/P3，快照校验）：** 为持久化配置定义运行时 schema，在任务选择、依赖计算及执行前校验完整形状；覆盖固定频道、Feed、`classification`、`ranking`、各预算正整数及允许范围，正则须可编译、排序来源须有效。不能只把 JSON 强转为 TypeScript 类型或只比较版本号。新增必需字段时明确提升执行 schema 版本，或为已知旧版本提供确定的兼容解析；缺字段、错误类型、未知版本及无效正则均通过租约保护终止对应任务，返回 `RULE_VERSION_UNSUPPORTED`，保留旧版及成功快照，不能回填当前配置继续旧游标。验收同版本号但缺少分类/排序字段的旧快照，确认不变成笼统内部错误或在领取任务前反复崩溃。

发布方式：

1. 各来源任务分片写 observations，结束后标成功；失败任务的暂存数据不作为成功来源使用。
2. 一个频道依赖的来源任务均成功或结束重试后，选择当日成功来源及仍在有效期内的最近成功来源。
3. 生成新的 `draft` edition，分批写入固定展示字段和最多 20 个条目；校验去重、排名、引用和新旧来源时间。
4. 原子更新该 edition 为 `published`。GET 只查询每频道最新已发布日期及修订版本，所以永远不会读到半份新榜单。
5. 全部来源都失败时不创建新的「今日」榜单，继续返回旧 edition 及单独的最新同步失败状态。
6. 重试成功可以产生新的修订版；旧版不覆盖，之前的来源快照和有效增长基线也不覆盖。

## 6. 调度、资源预算与恢复

### 6.1 调度

- 保留现有 `*/10 * * * *`，新增 `5-55/10 * * * *`，使热点调用与原任务在时间上错开 5 分钟。
- Worker `scheduled` 根据 `controller.cron` 精确分派。原 Cron 只调用 `runCronJobs`，新增 Cron 只调用 `runDiscoveryScheduled`。
- **补充于设置页增补（§21）：** 新 Cron 先读取实例的有效热点开关：已保存 `settings.discovery.enabled` 优先，缺记录才回退 `DISCOVERY_ENABLED`。设置读取合并在现有模块状态查询中，启用轮次不增加 SQL；关闭轮次执行一条计入预算的 SQL，不启动或续跑热点同步，外部请求为零。仍须重新验证 D1=16 的推进和收尾。
- 新 Cron 在北京时间 08:00 后首次触发时创建当天任务，正常起点约 08:05；全部日期由明确的 `Asia/Shanghai` 计算，Cloudflare 的 cron 表达式按 UTC 调度。
- 同一天任务依靠数据库唯一键只创建一次，之后各轮只续跑未完成任务。首次部署在当天 08:00 之后，由下一个热点轮次补建当天任务；不自动回补多个历史日期。
- 未到 08:00 时仅恢复上一日尚未到终止期限的任务。一次更新从启动起以 6 小时为完成目标，采集必须提前为来源终止、四频道发布和清理预留时间；未完成来源按失败保旧处理，避免无限等待。下一日创建新任务。具体收尾与错过触发策略见 R14。
- **补充于第三轮评审 R14（期限与收尾）：** 六小时验收覆盖来源终止、四频道发布任务终结及清理；全源失败时发布任务可以失败并保旧，不能为满足轮次伪造版本。单轮只做一个阶段时，终止来源本身也占一轮，需按「终止 + 四发布 + 清理」六个时间片计算：正常十分钟间隔应最迟在 `deadline-50 分钟` 开始收尾，第 32 轮上限与时钟截止取更早者。如果合并终止与首个发布，须另证单轮 SQL/请求预算及租约仍满足。触发延迟或缺失时按剩余真实时间判断，不依赖累计轮数；过期后停止采集和新版本发布、标明期限错误并保留旧版，清理可在后续有界维护轮次恢复，记录为降级而非六小时正常完成。验收包含部分成功、全失败、少于 32 次调用以及错过触发的时钟场景，并断言任务 `finished_at` / 版本 `published_at`。
- 错开触发不能替代锁。任务使用 D1 原子条件更新获得 2 分钟 lease，每片控制 60 秒以内；所有检查点写入检查 lease token，防止过期执行者覆盖新执行者。
- **补充于评审 R2：** 租约防护覆盖 observations/池状态写入、游标、任务完成和发布状态变更；写入条件同时校验 token、未到期及允许的任务状态，不能只保护最后一条检查点。Draft 写入及发布同样使用领取者令牌，过期执行者不得把旧 Draft 标为 published；验证失败则本片停止。

| 资源                       | 初始上限                                               |

| 单 Cron 轮次 D1 语句       | 40 条上限；batch 中每条语句分别计数                    |
| 单轮最大同时出站连接       | 3                                                      |
| 单轮 GitHub 搜索           | 最多 4 次，独立尊重 search 限额                        |
| 全模块每日外部请求         | 320 次硬上限，包含重试；达到后停止新请求并记录降级状态 |
| GitHub 搜索 / 补充仓库请求 | 最多 16 / 80 次每日                                    |
| HN 候选详情                | 最多 40 个，所有频道共享                               |

上述是应用上限，不代表平台允许每轮一定处理到上限。免费 Workers 当前 Cron CPU 只有 10 ms、外部子请求 50 次；D1 Free 每次 invocation 最多 50 条查询，单 SQL 绑定参数最多 100。实现采用少量多行写入，按参数数目拆批，并按任务阶段分开抓取/解析/发布。[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)、[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

RSS 解析先单 Feed 一片；GitHub/HN 初始每片处理至多 10 条内容，25 请求仅作硬上限。每轮至少推进一个可运行片，先完成一个频道的 GitHub 分区和共享 HN，来源之间轮转以防饥饿；预算和实测 CPU 有余量才处理第二片。

容量基线按一轮一片估算：GitHub 最坏 8 个补充详情片、HN 4 个详情片及 1 个列表片、搜索最多 4 片、RSS 3 片、发布 4 片、清理 1 片，合计 25 片；6 小时约 36 轮，为重试留有余量。来源只读阶段可进一步减少已被搜索返回的仓库补抓。**补充于第三轮评审 R14：** 到第 32 轮或完成期限前 50 分钟（取更早者），剩余来源终止采集，优先发布已完成来源与可用旧来源，计入终止及清理轮次。

P3 必须用最大池规模和真实资源统计验证期限。**补充于第三轮评审 R12（消除范围冲突）：** 上线前实测 CPU；若须缩小片大小，仍按已确认的 GitHub 80 / HN 40 / 三个 RSS 来源重新验证期限，优先优化或评估满足原范围的 Workers 套餐。任何缩候选池或停用来源都作为单独的范围变更，先记录取舍并取得用户确认，再按新范围重验；不自动减成 GitHub 40 / HN 20，也不将其算作原方案验收通过。无法满足目标套餐时保持开关关闭，不能宣称 Cron 天然绕过免费限制。

**补充于复审 R10（P3，冻结参数的消费闭环）：** 将上述数值保留为不可突破的安全上限，实际执行限制取安全上限与已验证配置限额中的较小值。任务恢复时，分类、来源内排序、6:3:1 交错、新发现名额、条数、片大小及并发均显式使用该任务的快照，不依赖函数默认的当前 `DISCOVERY_CONFIG`。实际调用日的模块预算须在当日预算行固化，并约束所有新旧任务的请求预占；跨午夜按新调用日预算行计数，任务来源/排序规则仍用自己的快照。请求、search/detail 分项、D1 计数及预占批次均服从有效上限，不能因一次预占 5 个而越过下调后的剩余额度。验收用较低预算和不同排序快照运行，途中改变当前配置，检查旧任务输出及各计数仍符合冻结参数；同时验证配置调大也无法突破 25/320/40/3、GitHub 16/80 等硬上限。

**补充于第三轮评审 R15（可执行下限）：** 当前执行器接受的 D1 单轮限额最小为 16，最大有效值 40；其余预算为正整数并受对应硬上限约束。下调仍须为 bootstrap、原子归并/发布和租约收尾预留语句，不能在接受配置后反复耗尽预算且不推进。低于 16 的新配置或持久化快照在执行前明确拒绝并保旧，不能提升到当前默认值继续。P3 除空来源下限测试，还需以 16 条 D1 预算覆盖最大池、非空 HN/RSS、URL 归并、发布及清理，实际物理 SQL 与报告数一致；无法完整结束时须按冻结预算确定推进/期限降级并保旧，不得超额或无限续跑。片大小为 1、单轮请求为 1 等合法低预算也须验证有界推进和最终截止策略，不能宣称所有低预算都能完成原规模当日榜单。

**补充于复审 R8（P5，上线阻塞）：** 当前不能判定本功能可按 Workers Free 稳定启用。本地 workerd profiler 的 30 条 RSS 冷启动 sampled JS 为 Hugging Face 11.352 ms、Cloudflare 18.748 ms；仅将 RSS 限额改为 10/5 条的对照中，Cloudflare 仍为 14.469/15.686 ms。采样有噪声、未包含 D1，不能等同平台 CPU 账单或证明生产必然超限，但不足以通过免费版 10 ms 门槛。[Workers CPU 限制与观测方式](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)

### 6.3 恢复与数据寿命

- 游标、候选 ID、计数和重试时间写 D1；不能只依赖内存锁或一次 `waitUntil` 长链。
- 429、GitHub 限流及短暂 5xx 最多重试 3 次，按 `Retry-After` / reset 等返回头与退避时间续跑，不在 Worker 内长时间 sleep。
- 来源正常返回零候选是一次成功的空结果，和请求失败分别处理；成功空结果可以替换该来源的旧内容。
- 某来源失败不会阻塞其他频道及来源；失效 Feed 不清空历史榜单。
- **补充于评审 R6：** HTTP 请求不承担抓取任务，本期不新增运维触发端点。开发环境用 Wrangler scheduled 测试路径及可注入时钟验证；生产首次同步由启用后的下一次热点 Cron 创建并分片推进，当天未到 08:00 则等待约 08:05。运维通过已有日志和发现读接口检查任务/版本状态；本地 scheduled 测试不能当作生产初始化完成的证据。
- 请求预算以实际发起请求的北京时间日期对应的 `__budget__` 行原子预占，每次预占下一组最多 5 个请求；未消费的额度保守计入，以防中断后少计。budget 行同时持有模块运行 lease，限制热点轮次并发；具体来源任务仍有各自 lease 与断点。跨午夜停止当前片，下轮按新调用日重新领取预算，来源任务的 `edition_day` 保持原值。重试不得重置预算，抓取与无抓取的解析/发布片分开。
- 快照、任务及发布版本保存 30 天；分片清理，先删除过期版本条目，再删除不被保留版本引用的快照/任务，最后删除无引用内容。保证最近成功回退版本至少保留，避免清理破坏来源引用。
- 日志包含日期、频道、来源、阶段、请求数、耗时、成功/失败数量和错误码；不包含凭证。

## 7. API 与收藏契约

| 方法 / 路径                     | 契约                                                                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/discovery/channels`   | 四个固定频道及功能启用状态，不包含可编辑规则；`enabled` 对应实例有效开关，`ready` 表示发布就绪，导航要求两者均为 true |
| `GET /api/discovery?channel=ai` | 最新已发布频道版本、最多 20 个条目、来源新旧时间、当前任务状态；不接收 `q`、关键词、自定义 URL                                                          |
| `GET/PUT /api/settings/discovery` | 登录用户读取或保存 `{ enabled: boolean }`，返回有效 `enabled` / `ready`；使用 `requireAuthWrite`、`private,no-store`，无公开写权限，保存不发起来源抓取 |
| `POST /api/bookmarks`           | 继续使用现有 URL 收藏接口，不新建另一条写入收藏路径                                                                                                     |

读接口复用 `requireAuthOrPublicRead`。当前收藏/已收藏状态通过规范化身份与已有收藏匹配能力批量计算，不逐条查库；访客不返回私人收藏状态，收藏按钮触发既有登录引导。响应契约用共享 Zod schema，错误格式与当前 API 一致。

**补充于评审 R1（服务端）：** 「批量匹配」是在发现 repository 对当前最多 20 条内容及其已知别名执行有界批量查询，排除软删除收藏，已归档但未删除的收藏仍算已收藏；不调用或改造供扩展使用、读取全量收藏的 `/bookmarks/match-index`。匹配不改变原收藏身份规则或恢复行为，来源 URL 到收藏身份的转换只放在发现适配层。

收藏成功后刷新收藏相关 Query Cache 和当前热点的收藏状态；重复收藏 `409 DUPLICATE` 根据现有响应 ID 更新为「已收藏」。软删除收藏应沿用现有恢复行为，并在实施时验证，而不是由发现模块自行恢复。Feed 和 HN 的外链指向 GitHub 时由现有 `detectSourceType` 识别为 GitHub 收藏；其他文章为 `url`，不扩展现有 `source_type` 枚举。

发现响应不能进行跨访客/登录用户缓存串用；第一版浏览器按频道缓存 5 分钟，服务端响应使用私有/不可共享缓存语义。站点 Service Worker 继续不缓存 `/api`。

**补充于评审 R1（客户端）：** 带收藏状态的发现响应使用新增 `queryKeys.bookmarks.discovery(channel, accessScope, publicReadEnabled)`，保持在已有 `bookmarks` 前缀下；`accessScope` 区分 `guest` 与已确认的用户 ID。这样现有新增、删除、批量删除及恢复操作使 `bookmarks.all` 失效时，所有已缓存频道的收藏状态同步失效，无需改写各既有业务入口。频道清单使用独立 discovery key，并同样包含访问范围/公开读状态。身份尚未确定、公开读关闭或收到 401 时停止展示旧访问范围中的数据；身份变更重新请求，不使用旧范围的 placeholder。显式退出继续复用现有 `queryClient.clear()`；登录弹窗本身只更新 auth 缓存，不能依赖它刷新发现数据。5 分钟新鲜度用于内容；重新进入页面或窗口重新获得焦点时刷新收藏状态，以收敛扩展/导入等外部写入。所有刷新仍只读 D1。

**补充于评审 R5（mock）：** `api.createBookmark` 当前 mock 分支把所有输入写成 `source_type=github` 并拼接 GitHub URL；P4 必须在该分支补足普通 `url` 内容的类型、规范化 URL 与重复身份处理，已有 GitHub 输入继续保持原有行为及返回形状。发现 mock 的已收藏状态从同一 mock store 计算，不能使用独立假收藏集合；覆盖 GitHub 仓库和 RSS/HN 普通文章各一次收藏、重复收藏与删除后状态刷新。
